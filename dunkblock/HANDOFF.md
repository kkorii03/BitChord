# DunkBlock 인수인계 문서

이 파일 하나만 읽으면 프로젝트를 이어받을 수 있게 썼다. 사람이든 AI든 **이 파일부터** 읽고, 필요한 세부는 링크된 문서를 본다.
마지막 갱신: 2026-11-10.

## 1. 무엇을 만드는가

모바일 농구 게임 **덩크시티 다이너스티**(3:3)에서, 사용자가 손으로 이동하는 동안 **블록 버튼만 자동으로 누르는** 안드로이드 앱.

고정 조건:
- 기기: Galaxy S24 Ultra (SM-S928N), Android 17 / API 37, 1440x3120 @ 120Hz. 루팅 금지, 게임 변조·메모리 접근 금지.
- 이동 조이스틱과 수비 위치는 사용자가 직접 조작한다. 자동화 대상은 블록 버튼뿐이다.
- 대량 수동 라벨링·서버 인프라·무거운 AI는 피한다. 측정으로 확인되지 않은 것을 가능하다고 말하지 않는다.
- 사용자는 한국어로 소통하며 개발자가 아니다. 지시는 "버튼 누르고 1판 하면 됩니다" 수준으로 구체적이어야 한다.
- 사용자 선수: 올드 르브론(360° 블록 가능 → 각도 판정 불필요, 거리만 중요).

## 2. 저장소와 빌드

- `data/labels/`: 영상 판독 결과(영상 원본은 저장소에 없다. 사용자가 보낸 화면 녹화다).

빌드·배포:
- CI: `.github/workflows/dunkblock-apk.yml`. push하면 core 테스트 → 분석기·영상 파이프라인 자체 검증 → 두 APK 빌드.
- 개발 세션에서는 Android SDK와 CI 아티팩트 저장소에 접근할 수 없었다. 그래서 **커밋 메시지에 `[ship-blocker]`, `[ship-bench]`, `[ship-apk]`(둘 다)를 넣으면 CI가 APK를 `dunkblock/dist/`에 커밋**하고, 사용자는 raw 링크로 받는다:
  `https://raw.githubusercontent.com/kkorii03/BitChord/ccr-8af48de0-9efnr2/dunkblock/dist/<파일명>`
- APK를 커밋할 때마다 저장소가 약 28MB씩 커진다. 꼭 필요할 때만 ship한다.
- 서명: `app/signing/bench.p12`(저장소에 있는 시험용 고정 키). versionCode = 1000 + CI 실행 번호 → 덮어 설치 가능.
- 로컬에서 core만: `DUNKBLOCK_CORE_ONLY=1 ./gradlew :core:test`. Android 코드는 로컬 컴파일이 안 되므로 CI가 유일한 컴파일 검사다.

## 3. 확인된 사실 (실측)

화면 캡처 (MediaProjection, 배율 0.5 = 1560x720):
- 120fps, 표시 프레임 3050/3050 수신(누락·중복 0). 프레임 생성 → 앱 도착 0.33ms.
- 게임 화면 캡처 가능(검은 화면 0.4%). 처리 시간: 분석 평균 2.1ms / p95 3.8ms(경기 중).
- 표시 시각 대비 지연은 추정만 가능(±1프레임).
- 경기 1판에 열 상태 2 → 3, 배터리 39.8 → 42.8°C.

입력 (AccessibilityService.dispatchGesture):
- **같은 창에 실제 손가락이 있으면 주입 탭이 그 손가락을 취소한다(24/24).**
- **손가락이 접근성 오버레이(다른 창)에 있으면 취소되지 않는다(반복 확인).**
- 그래서 "대리 조이스틱"을 쓴다: 오버레이 패드가 엄지를 받고, 서비스가 `continueStroke`로 조이스틱 입력을 이어서 주입한다(16ms 조각).
  - 길이 0인 조각은 취소된다 → 엄지가 멈추면 1px 흔들기. 좌표는 정수로.
  - **블록 탭은 조이스틱 조각과 같은 제스처에 넣되 2ms 늦게 시작해야 한다**(0ms 시작: 0/4, 2ms: 8/8).
  - 패드를 조이스틱 위에 겹치고, 엄지가 닿으면 패드를 `FLAG_NOT_TOUCHABLE`로 바꿔 주입 입력을 통과시킨다.
  - 실제 게임(연습 모드): 1801조각 취소 0, 블록 10/10, 사용자가 캐릭터 이동과 블록 점프 확인.
  - 지연: 블록 탭 도착 약 15ms, 이동 추종 약 20ms(추정).
- 구현: `BlockAccessibilityService.ProxyStick`, `InGameProxy`. 화면 위치(가로 3120x1440): 조이스틱 (645,1108), 블록 (2774,1203).

게임에 대해 (사용자 설명 + 영상 판독, 자세히는 `docs/GAME_FLOW.md`):
- 내 선수 한 명만 조작. 블록 버튼은 누르는 즉시 점프. "슛은 생각보다 빨리 뛰어야 막힌다."
- 게임이 판정을 글자로 띄운다: **"블록"(성공 시에만)**, "무리한 블록", "컨테스트", "강한 컨테스트", "드리블 불가", "리바운드 거리 부족".
- 상대 선수는 빨간 윤곽선, 발밑에 팀 색 링. 공은 검정+노랑.
- **상대 궁극기: 화면 전체가 약 0.96초 어두워진다**(격자 밝기 105 → 21~30). 다른 5개 영상은 101 아래로 내려간 적 없음.
- 리플레이는 1배속. 갤럭시 화면 녹화는 약 120fps 가변 프레임.
- 블록은 드물다: 한 판에 한 번 나올까 말까(랭커도).

블록 타이밍 판독 (2건뿐):
- 무리한 블록: 수비수가 슈터보다 약 270ms 늦게 뜸.
- 깔끔한 블록(상대 궁극기 슛): 수비수가 슈터보다 약 50~80ms 먼저 뜸. 어두워짐 시작 후 약 0.64초.

실기기 vc1022 2판 (11-10 16:26 연습 모드 104초, 16:29 3:3 경기 182초, 사용자 묶음 `DunkBlock_send_20261110_163312.zip`):
- 플레이 중 화면 = 리플레이와 비슷한 측면 중계 시점. 내 선수는 발밑 파란 원 + 이름(SF 제임스). 점수판 가운데 샷 클락 옆 삼각형이 공격권 방향.
- 수비 중 오른쪽 버튼: 수비 / 가속 / 스틸 / 전면 블록 / 스킬(제왕 사이드 숏 게이지). 공격 중 버튼은 아래 참고.
- **상대 슛이 나가면 게임이 버튼을 바꾼다**: 수비→박스아웃(클립 3개 모두), 전면 블록→리바운드(1개). 시점은 공이 손을 떠날 즈음이라 발동 신호로는 늦다. 슛 자동 라벨로 쓸 수 있다. 정밀 판독 1건: 공을 머리 위로 든 때가 박스아웃 전환보다 약 300ms 앞.
- 궁극기 감지 10회 중 누름 2회(둘 다 연습 모드, 2초 뒤 사진에 "블록 위치 부족"), 8회는 엄지가 조이스틱에 없어 건너뜀. 감지 중 3회는 로딩 화면 깜박임(어두움 0.15~0.53초). 진짜 궁극기 어두움: 경기 0.85초, 연습 모드 약 1.67초.
- **사용자 보고: 이동 중 패스·가속을 누르면 캐릭터가 멈춘다.** 원인 추정: 게임 창에 실제 손가락이 닿으면 주입 중인 조이스틱이 끊김(시스템 취소 보고는 0회였으므로 게임 쪽에서 버리는 것으로 보임, 미확인).
- 기록 클립은 흑백 640px라 공이 잘 안 보임. 묶음 크기 제한으로 클립 1~9가 빠짐.
- 사용자는 vc1022에서 우리 팀 슛에도 '기록'을 눌렀다(11-10). 다음부터는 상대 슛만 누르기로 함. vc1026부터 기록 클립 태그에 공격/수비가 붙는다(mark_def / mark_off / mark_unk).
- **공격 중 버튼**: 스크린 / 가속 / 패스 요청 / 슛. 블록 자리(blockFx,blockFy)에 "슛"이 오고 공을 가졌을 때는 버튼 위쪽에 주황 공이 보인다. 우리 팀 다른 선수가 공을 가지면 슛 버튼이 회색이다.
- **공격/수비 판별(60장 컬러 화면 실측)**: 블록 자리 원(반지름 0.045W) 안의 어두운 픽셀(R,G<70,B<90) 비율이 수비 활성 0.24, 공격 0.04~0.08, 회색 버튼 0.01~0.03이다. 주황(R>190, G 80~190, B<90) 비율은 공을 가진 공격에서 0.02, 수비에서 0이다. 규칙: 어두움 >0.15이고 주황 <0.005면 수비, 주황 >0.01이면 공격, 나머지는 모름(준비 단계·재사용 대기). 오판은 0건이었다.
- **빨간 공 표시**: 상대 팀이 공을 가지면 공 위에 빨간 원판(공 아이콘이 들어 있음, 960폭 기준 지름 18~28px)이 뜬다. 상대가 슛하면 공을 따라 공중으로 날아간다(111.8초, 117.8초 화면). 그래서 공이 손을 떠나는 순간을 화면만으로 잡을 수 있다(추정, 연속 프레임으로는 미확인). 우리 팀 쪽 파란 표시는 코트와 하늘의 파란색에 묻혀 색으로는 찾을 수 없다.
- 빨간 원판 찾기 원형(PC, 같은 60장): 색 R>160, G<25, B 30~90, R−B>95. 거친 격자(2px)에서 0.0104W 크기 창의 채움 비율이 가장 높은 곳을 찾는다. 채움 ≥0.45이고 두 번째 덩어리 ≤ 0.6×최고일 때만 인정한다. 보이는 원판 9개를 찾았고(채움 0.47~0.94) 오탐은 0개였다. 멀리 있는 원판은 채움 0.47~0.53이라 문턱 여유가 작다.

## 4. 시도했고 실패한 것 (다시 하지 말 것)

- 유튜브 다운로드: 개발 세션 네트워크가 YouTube를 차단(프록시 403). 사용자가 MP4를 첨부해야 한다(30MB 이하).
- 화면 전체 움직임 감지: 3:3에서는 항상 어딘가 움직여서 무의미(6분 40초에 65건).
- 색으로 공 찾기: 실제 영상에서 정밀도 약 20~25%(노란 관중석·신발·배지). 쓸 수 없음.
- "빨간 윤곽선 덩어리가 솟구침" 발동 규칙: 초당 약 4회 발동. 쓸 수 없음.
- "몸과 발밑 링 사이 틈" 발동 규칙: 9개 영상 중 1개만 검출.
- '컨테스트' 글자 견본 매칭: 2건 중 0건 검출(기울어진 분홍 띠 위 글자).
- 흰 실루엣 번쩍임은 슛 신호가 아니다(패스 전에도 나옴).

## 5. 지금 있는 것

- **DunkBlock(blocker) 초안**: 상대 궁극기(화면 어두워짐)를 감지하면 설정 지연(기본 600ms) 뒤 블록을 누른다. `AutoBlocker.kt`.
  - 11-10 변경(실기기 미검증): 누르는 순간에도 아직 어두워야 누른다(로딩 깜박임 제외). 엄지 조건 대신 "8초 안에 받침판을 만졌음"이면 누른다.
  - 11-10 변경: **오른쪽 버튼 받침판**(`InGameProxy.showButtonTiles`, 화면 오른쪽 아래를 투명 창 4개로 덮음). 손가락이 닿으면 그 창을 통과 모드로 바꾸고 40ms 뒤 같은 자리를 주입한다. 조이스틱·버튼·자동 블록이 모두 `ProxyHand`의 한 제스처(여러 획)로 나간다. 획 여러 개를 동시에 이어 보내는 것은 처음이라 `ingame_proxy_events.csv`와 요약의 취소·거부·"받침판에 떨어짐" 수로 확인할 것. 버튼 반응이 약 40ms 늦어진다.
  - **일반 슛 발동 규칙 v1(11-10, 측정 전 추정값, `ShotWatcher.checkShot`)**: 최근 1초 안에 수비였고 공격이 아닐 때, 빨간 원판이 "갑자기 위로" 움직이면 바로 블록을 누른다(모으기·점프). 기준(민감도 보통): 최근 약 100ms 상승 속도 ≥0.35 화면높이/초, 그 앞 200ms보다 ≥0.25 빨라짐, 150ms 상승 ≥0.025H, 가로보다 세로가 큼. 원판이 위아래로 4번 이상 뒤집혔으면(드리블) 상승 기준을 1.6배로 올린다. 모으기를 놓치면 공이 날아오를 때(0.9H/s 초과) 늦은 대비로 누른다. 1.5초에 한 번만 누른다. 앱 화면 "일반 슛 (시험)"에서 켜기·민감도(낮음/보통/높음)·추가 지연(0~200ms)을 바꿀 수 있고, "블록 실제로 누르기"가 꺼져 있으면 기록만 한다. 요약에는 모으기 감지가 공이 떠나기보다 얼마나 앞섰는지(중앙값), 감지했는데 공이 안 떠난 횟수(오발 추정), 미리 못 잡은 슛 수가 남는다. 발동 때마다 trig_gather/trig_release 클립과 컬러 확대를 저장한다. 거리(내 선수와 슈터)는 아직 보지 않는다.
  - 기존 설명: 거리, 공격/수비 구분, 누구의 궁극기인지도 보지 않는다(궁극기 규칙).
  - 11-10 vc1026 `ShotWatcher.kt`(자료 수집만, 누르지 않음): 약 60Hz로 공격/수비 판별과 빨간 원판 위치를 `shot.csv`에 매 프레임 적는다. 원판이 들고 다니는 속도보다 빨리 움직이면(0.9 화면높이/초 초과) `shot_events.csv`에 disc_fast로 적는다. 그중 수비 중이고 위로 날아간 것은 shot_candidate로 표시하고, 흑백 클립 "shot"(앞 1.6초)과 그 순간 컬러 화면 1장을 저장한다. 기록·press 클립 태그에는 공격/수비가 붙는다. 처리 시간은 요약에 평균과 최대로 남는다. 사용자 요청("프로토타입이니 로그를 최대한")으로 더한 것: shot.csv에 판별 원값(dark, orange)과 수비/박스아웃 자리(블록 자리 + (-0.09W, -0.21H), 추정)의 밝기·어두움 비율을 매 프레임 남긴다. `colour/colour_NN_태그_시각/`에는 공 주변(0.16W × 0.34H, 원래 해상도) 컬러 화면을 약 30Hz로, 슛 후보·기록·궁극기 때 직전 최대 3.1초 분량을 저장한다(최대 20개, `crops.csv`에 자른 위치). 묶음에서 컬러 확대는 흑백 클립보다 먼저 담긴다.
  - 실행 중 기록(세션 폴더): `frames/` 2초마다 컬러 화면, `clips/` 640px 흑백 클립(태그 press=버튼 변화, ult=궁극기 감지 앞 1.0초~뒤 2.6초, mark=사용자가 화면의 '기록' 버튼을 누른 직전 3.4초), `clips.csv`, `autoblock.csv`(감지·누름 시각), `presses.csv`, `frames.csv`(프레임별 밝기·버튼 밝기·처리 시간), `seconds.csv`(발열), 그리고 `*_ingameproxy/ingame_proxy_events.csv`(엄지·주입 이벤트). 시각은 모두 `System.nanoTime()` 기준이라 서로 맞춰 볼 수 있다.
  - 실기기 검증 전이다(작성 시점 기준).
- `dunkvideo`: "블록"/"무리한 블록" 글자 자동 탐지는 9개 영상에서 정확(블록 있는 8개에서 1개씩, 없는 1개에서 0개).

## 6. 다음에 할 일 (우선순위)

0. **받침판 빌드 실기기 확인**: 이동하며 패스·가속, 궁극기 자동 블록. 요약의 취소·거부 수와 사용자 관찰.
1. **vc1026 묶음 결과(11-10 17:19 받음, 연습 약 290초 + 경기 2판, 633초)**: 사용자 기록 7회(전부 경기 중, 317~593초). 기록은 슛 뒤 1~4초에 눌림. 슛 후보(수비 중 위로 빠르게)는 21회, 기록 7회 중 4회 앞에 후보가 있었다(그중 1회는 판별이 unk). 규칙 v1을 `shot.csv`로 다시 돌려 보니(PC 모의, `scratchpad\simtrig.ps1`) 경기 중 발동 16회, 기록 7회 중 5회 앞에서 발동(놓친 2회: 313초 판별 unk, 522.9초). 기록 없는 발동 11회 중 일부는 기록 안 한 실제 슛으로 보인다(423.9→425.1, 449.0→449.8 = 모으기 감지가 공이 떠나기 0.8~1.1초 앞, **너무 이를 수 있음**). 연습 모드에서 컴퓨터 궁극기가 8초마다 와서 흑백 클립 30개와 컬러 20개가 180초 안에 다 찼고 경기 장면 클립은 0개였다 → 종류별 몫(궁극기 6, 버튼 변화 8, 컬러 궁극기 3)으로 고침. 원판은 슈터 쪽에서만 잡히고 프레임의 약 18%에서 보인다(구멍이 많음).
   - 다음 묶음에서 볼 것: trig 클립으로 모으기 감지 시각과 실제 점프 시각의 차이, 이른 발동이면 추가 지연 범위를 늘리거나 "공이 떠나기 직전" 쪽으로 기준을 옮긴다.
2. **실제 슛 발동 규칙(라이브)**: 수비 중 + 원판이 내 선수와 가까움(파란 발밑 원, 아직 설계 안 함) + 원판 상승 시작 → 측정된 지연 뒤 블록. 공이 손을 떠난 뒤에 누르면 늦을 가능성이 크다(박스아웃 판독: 들어 올림이 약 300ms 앞). 처음에는 그림자 모드로 would_press만 적어 오탐을 잰다.
3. **일반 슛 발동 신호(예전 후보).** 후보: 상대(빨간 윤곽선) 선수의 자세 변화를 더 정교하게(사전학습 자세 모델 검토), 드리블이 멈추는 순간, 샷 클락 원. 판정 글자("블록")로 성공 장면을 자동 수집해 타이밍 표본을 늘린다.
4. **앱 안에서 "블록" 글자 감지**해 성공 여부를 자동 기록(지금은 PC 파이프라인만).
5. 블록 타이밍 표본 늘리기: 슛 종류별, 깔끔한 블록과 무리한 블록의 점프 시점 차이.
6. 발열 대책: 필요 없는 분석 끄기(blocker는 이미 모션 분석 끔).

## 7. 정직성 규칙 (이 프로젝트의 약속)

- 실측과 추정을 구분해 말한다. 분석하지 않은 것을 분석했다고 하지 않는다.
- 영상에서는 버튼을 누른 시각을 알 수 없다. 점프가 보인 시각만 안다.
- 표본 수를 같이 말한다(예: "영상 1개 기준").
- 사람과의 공식 경기에서 자동 입력을 쓰면 운영정책 위반으로 제재될 수 있다. 사용자에게 매번은 아니어도 분명히 알려 둔다. 약관은 확인하지 못했다.
