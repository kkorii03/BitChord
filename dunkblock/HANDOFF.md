# DunkBlock 인수인계 문서

이 파일 하나만 읽으면 프로젝트를 이어받을 수 있게 썼다. 사람이든 AI든 **이 파일부터** 읽고, 필요한 세부는 링크된 문서를 본다.
마지막 갱신: 2026-11-10.

## 1. 무엇을 만드는가

모바일 농구 게임 **덩크시티 다이너스티**(3:3)에서, 사용자가 손으로 이동하는 동안 **블록 버튼만 자동으로 누르는** 안드로이드 앱.

고정 조건:
- 기기: Galaxy S24 Ultra (SM-S928N), Android 17 / API 37, 1440x3120 @ 120Hz. 루팅 금지, 게임 변조·메모리 접근 금지.
- 이동 조이스틱과 수비 위치는 사용자가 직접 조작한다. 자동화 대상은 블록 버튼뿐이다.
- 대량 수동 라벨링·서버 인프라·무거운 AI는 피한다. 측정으로 확인되지 않은 것을 가능하다고 말하지 않는다.
- 사용자는 한국어로 소통하며 개발자가 아니다. 지시는 "버튼 누르고 1판 하면 됩니다" 수준으로 구체적이어야 한다.
- 사용자 선수: 올드 르브론(360° 블록 가능 → 각도 판정 불필요, 거리만 중요).

## 2. 저장소와 빌드

- 저장소 `kkorii03/BitChord`, 브랜치 `ccr-8af48de0-9efnr2`, 폴더 `dunkblock/` (루트의 BitChord 프로젝트와 무관한 독립 Gradle 빌드).
- `core/`: 순수 Kotlin(JVM). 통계, 프레임 로그, 패턴 코덱, 모션, 분석 보고서. 단위 테스트 있음.
- `app/`: Android. 제품 플레이버 2개가 같은 코드를 쓴다.
  - `bench` → **DunkBlock Bench** (`dev.dunkblock.bench`): 측정·실험 앱. 화면은 `MainActivity`.
  - `blocker` → **DunkBlock** (`dev.dunkblock.blocker`): 자동 블록 앱. 화면은 `src/blocker/.../BlockerActivity.kt` (iOS식 UI).
- `tools/analyze.py`: 앱이 내보낸 CSV 재계산. `tools/video/dunkvideo`: 영상 → 타이밍 데이터 파이프라인.
- `docs/`: `FEASIBILITY.md`(초기 판정), `MEASUREMENT_GUIDE.md`, `RESULTS_round1.md`(실측 기록), `GAME_FLOW.md`(게임 사실과 영상 판독).
- `data/labels/`: 영상 판독 결과(영상 원본은 저장소에 없다. 사용자가 보낸 화면 녹화다).

빌드·배포:
- CI: `.github/workflows/dunkblock-apk.yml`. push하면 core 테스트 → 분석기·영상 파이프라인 자체 검증 → 두 APK 빌드.
- 개발 세션에서는 Android SDK와 CI 아티팩트 저장소에 접근할 수 없었다. 그래서 **커밋 메시지에 `[ship-blocker]`, `[ship-bench]`, `[ship-apk]`(둘 다)를 넣으면 CI가 APK를 `dunkblock/dist/`에 커밋**하고, 사용자는 raw 링크로 받는다:
  `https://raw.githubusercontent.com/kkorii03/BitChord/ccr-8af48de0-9efnr2/dunkblock/dist/<파일명>`
- APK를 커밋할 때마다 저장소가 약 28MB씩 커진다. 꼭 필요할 때만 ship한다.
- 서명: `app/signing/bench.p12`(저장소에 있는 시험용 고정 키). versionCode = 1000 + CI 실행 번호 → 덮어 설치 가능.
- 로컬에서 core만: `DUNKBLOCK_CORE_ONLY=1 ./gradlew :core:test`. Android 코드는 로컬 컴파일이 안 되므로 CI가 유일한 컴파일 검사다.

## 3. 확인된 사실 (실측)

화면 캡처 (MediaProjection, 배율 0.5 = 1560x720):
- 120fps, 표시 프레임 3050/3050 수신(누락·중복 0). 프레임 생성 → 앱 도착 0.33ms.
- 게임 화면 캡처 가능(검은 화면 0.4%). 처리 시간: 분석 평균 2.1ms / p95 3.8ms(경기 중).
- 표시 시각 대비 지연은 추정만 가능(±1프레임).
- 경기 1판에 열 상태 2 → 3, 배터리 39.8 → 42.8°C.

입력 (AccessibilityService.dispatchGesture):
- **같은 창에 실제 손가락이 있으면 주입 탭이 그 손가락을 취소한다(24/24).**
- **손가락이 접근성 오버레이(다른 창)에 있으면 취소되지 않는다(반복 확인).**
- 그래서 "대리 조이스틱"을 쓴다: 오버레이 패드가 엄지를 받고, 서비스가 `continueStroke`로 조이스틱 입력을 이어서 주입한다(16ms 조각).
  - 길이 0인 조각은 취소된다 → 엄지가 멈추면 1px 흔들기. 좌표는 정수로.
  - **블록 탭은 조이스틱 조각과 같은 제스처에 넣되 2ms 늦게 시작해야 한다**(0ms 시작: 0/4, 2ms: 8/8).
  - 패드를 조이스틱 위에 겹치고, 엄지가 닿으면 패드를 `FLAG_NOT_TOUCHABLE`로 바꿔 주입 입력을 통과시킨다.
  - 실제 게임(연습 모드): 1801조각 취소 0, 블록 10/10, 사용자가 캐릭터 이동과 블록 점프 확인.
  - 지연: 블록 탭 도착 약 15ms, 이동 추종 약 20ms(추정).
- 구현: `BlockAccessibilityService.ProxyStick`, `InGameProxy`. 화면 위치(가로 3120x1440): 조이스틱 (645,1108), 블록 (2774,1203).

게임에 대해 (사용자 설명 + 영상 판독, 자세히는 `docs/GAME_FLOW.md`):
- 내 선수 한 명만 조작. 블록 버튼은 누르는 즉시 점프. "슛은 생각보다 빨리 뛰어야 막힌다."
- 게임이 판정을 글자로 띄운다: **"블록"(성공 시에만)**, "무리한 블록", "컨테스트", "강한 컨테스트", "드리블 불가", "리바운드 거리 부족".
- 상대 선수는 빨간 윤곽선, 발밑에 팀 색 링. 공은 검정+노랑.
- **상대 궁극기: 화면 전체가 약 0.96초 어두워진다**(격자 밝기 105 → 21~30). 다른 5개 영상은 101 아래로 내려간 적 없음.
- 리플레이는 1배속. 갤럭시 화면 녹화는 약 120fps 가변 프레임.
- 블록은 드물다: 한 판에 한 번 나올까 말까(랭커도).

블록 타이밍 판독 (2건뿐):
- 무리한 블록: 수비수가 슈터보다 약 270ms 늦게 뜸.
- 깔끔한 블록(상대 궁극기 슛): 수비수가 슈터보다 약 50~80ms 먼저 뜸. 어두워짐 시작 후 약 0.64초.

실기기 vc1022 2판 (11-10 16:26 연습 모드 104초, 16:29 3:3 경기 182초, 사용자 묶음 `DunkBlock_send_20261110_163312.zip`):
- 플레이 중 화면 = 리플레이와 비슷한 측면 중계 시점. 내 선수는 발밑 파란 원 + 이름(SF 제임스). 점수판 가운데 샷 클락 옆 삼각형이 공격권 방향.
- 수비 중 오른쪽 버튼: 수비 / 가속 / 스틸 / 전면 블록 / 스킬(제왕 사이드 숏 게이지). 공격 중 버튼은 아직 못 봄.
- **상대 슛이 나가면 게임이 버튼을 바꾼다**: 수비→박스아웃(클립 3개 모두), 전면 블록→리바운드(1개). 시점은 공이 손을 떠날 즈음이라 발동 신호로는 늦다. 슛 자동 라벨로 쓸 수 있다. 정밀 판독 1건: 공을 머리 위로 든 때가 박스아웃 전환보다 약 300ms 앞.
- 궁극기 감지 10회 중 누름 2회(둘 다 연습 모드, 2초 뒤 사진에 "블록 위치 부족"), 8회는 엄지가 조이스틱에 없어 건너뜀. 감지 중 3회는 로딩 화면 깜박임(어두움 0.15~0.53초). 진짜 궁극기 어두움: 경기 0.85초, 연습 모드 약 1.67초.
- **사용자 보고: 이동 중 패스·가속을 누르면 캐릭터가 멈춘다.** 원인 추정: 게임 창에 실제 손가락이 닿으면 주입 중인 조이스틱이 끊김(시스템 취소 보고는 0회였으므로 게임 쪽에서 버리는 것으로 보임, 미확인).
- 기록 클립은 흑백 640px라 공이 잘 안 보임. 묶음 크기 제한으로 클립 1~9가 빠짐.

## 4. 시도했고 실패한 것 (다시 하지 말 것)

- 유튜브 다운로드: 개발 세션 네트워크가 YouTube를 차단(프록시 403). 사용자가 MP4를 첨부해야 한다(30MB 이하).
- 화면 전체 움직임 감지: 3:3에서는 항상 어딘가 움직여서 무의미(6분 40초에 65건).
- 색으로 공 찾기: 실제 영상에서 정밀도 약 20~25%(노란 관중석·신발·배지). 쓸 수 없음.
- "빨간 윤곽선 덩어리가 솟구침" 발동 규칙: 초당 약 4회 발동. 쓸 수 없음.
- "몸과 발밑 링 사이 틈" 발동 규칙: 9개 영상 중 1개만 검출.
- '컨테스트' 글자 견본 매칭: 2건 중 0건 검출(기울어진 분홍 띠 위 글자).
- 흰 실루엣 번쩍임은 슛 신호가 아니다(패스 전에도 나옴).

## 6. 다음에 할 일 (우선순위)

0. **받침판 빌드 실기기 확인**: 이동하며 패스·가속, 궁극기 자동 블록. 요약의 취소·거부 수와 사용자 관찰.
1. **슛 클립 자동 수집**: 수비→박스아웃 전환을 앱에서 감지해 직전 3초를 컬러·고해상도로 저장(지금 클립은 흑백 640px). 연습 모드 "수비 연습"에서 상대가 계속 슛하므로 표본 모으기에 적합. (실제 경기 화면은 11-10에 확보, 3절.)
2. **공격/수비 구분.** 공격 중에는 블록 버튼 자리에 다른 버튼(슛 등)이 있을 수 있다. 수비 때만 누르도록 버튼 모양이나 HUD로 구분해야 한다. 미확인.
3. **일반 슛 발동 신호.** 후보: 상대(빨간 윤곽선) 선수의 자세 변화를 더 정교하게(사전학습 자세 모델 검토), 드리블이 멈추는 순간, 샷 클락 원. 판정 글자("블록")로 성공 장면을 자동 수집해 타이밍 표본을 늘린다.
4. **앱 안에서 "블록" 글자 감지**해 성공 여부를 자동 기록(지금은 PC 파이프라인만).
5. 블록 타이밍 표본 늘리기: 슛 종류별, 깔끔한 블록과 무리한 블록의 점프 시점 차이.
6. 발열 대책: 필요 없는 분석 끄기(blocker는 이미 모션 분석 끔).

## 7. 정직성 규칙 (이 프로젝트의 약속)

- 실측과 추정을 구분해 말한다. 분석하지 않은 것을 분석했다고 하지 않는다.
- 영상에서는 버튼을 누른 시각을 알 수 없다. 점프가 보인 시각만 안다.
- 표본 수를 같이 말한다(예: "영상 1개 기준").
- 사람과의 공식 경기에서 자동 입력을 쓰면 운영정책 위반으로 제재될 수 있다. 사용자에게 매번은 아니어도 분명히 알려 둔다. 약관은 확인하지 못했다.
