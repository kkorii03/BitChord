# DunkBlock — 기술 실현 가능성 검토 (Phase 0)

> 이 문서는 **측정 전** 판단입니다. "확인됨"은 Android 공식 API/보안 모델에서 근거가 명확한 항목만,
> 나머지는 "미확인"으로 두고 어떤 측정으로 확인하는지 적었습니다. 수치는 하나도 실측값이 아닙니다.

## 1. 판정 요약

| # | 제약 / 질문 | 판정 | 근거 · 확인 방법 |
|---|---|---|---|
| 1 | 루팅 없이 다른 앱(게임) 메모리 읽기 | **불가능** | 앱마다 별도 UID + SELinux 샌드박스, 다른 프로세스 ptrace/`/proc/<pid>/mem` 접근 불가. 설계에서 제외 |
| 2 | 루팅 없이 게임 화면 캡처 | **가능(조건부)** | `MediaProjection` 공개 API. 매 세션 사용자 동의 필요(Android 14+는 토큰 1회용, 포그라운드 서비스 type=mediaProjection 필수) |
| 3 | 게임 화면이 실제로 찍히는가 | **미확인** | 게임이 `FLAG_SECURE`를 쓰면 검은 화면. → ① 게임 세션 요약의 "검은 화면 비율" |
| 4 | 캡처가 120FPS로 들어오는가 | **미확인** | 표시 120Hz ≠ 캡처 120FPS. 가상 디스플레이 합성 주기는 기기/OS 구현 의존. → ②의 카운터 기반 캡처 비율 |
| 5 | 화면 변화 → 앱 수신 지연 | **미확인(추정만 가능)** | 앱은 실제 발광 시각을 알 수 없음. Choreographer 예상 표시시각 기준 추정 + 외부 고속 촬영으로 검증 |
| 6 | OpenCV/경량 분석 10ms 이내 | **미확인** | → ③ 단계별 처리시간. 분석 해상도(축소)를 낮추면 대부분의 비용은 해상도와 무관하게 줄어듦(설계상) |
| 7 | 슛·덩크·레이업·페이크 구분 | **미확인 / 현 단계 미구현** | 학습 없는 차분 기반은 "움직임 발생"만 신뢰성 있게 잡음. 종류 구분은 Phase 5에서 데이터로 판단 |
| 8 | 루팅 없이 자동 터치 주입 | **가능** | `AccessibilityService.dispatchGesture()` (API 24+). 사이드로드 앱은 Android 13+ "제한된 설정" 해제 필요 |
| 9 | **수동 조이스틱 유지 + 자동 블록 탭 동시** | **미확인 — 실패 가능성 높음(추정)** | `dispatchGesture` 공식 문서에 "진행 중인 제스처는 사용자의 것이든 서비스의 것이든 취소된다"는 취지의 문구가 있음. 기기/OS 버전별 실제 동작은 → ④(앱 화면), ⑤(게임 화면) |
| 10 | 시스템 전체 CPU 사용률 | **불가능** | Android 8+에서 일반 앱의 `/proc/stat` 읽기 차단. 앱 자체 CPU 시간만 측정 |
| 11 | 게임 자체 FPS(120 유지 여부) 앱 내 측정 | **불가능(앱 단독)** | 다른 앱의 렌더 통계 접근 불가. 대체: 캡처 고유 프레임률(근사), PC의 `adb shell dumpsys SurfaceFlinger --latency` (루팅 불필요) |
| 12 | 캐릭터별 블록 각도(정면 180°/측면 포함/르브론 360°) 판정 | **미확인 — 추가 연구 필요** | 사용자 제공 정보. "언제" 외에 "지금 상대가 내 수비수의 블록 범위 안인가"가 필요 → 내 수비수 위치와 **바라보는 방향** 인식이 필요(아래 5절) |
| 13 | 게임 운영정책상 자동 입력 허용 여부 | **미확인** | 약관 직접 확인 필요. 일반적으로 온라인 대전 게임은 자동 입력을 금지하는 경우가 많고 계정 제재 위험이 있음. 이 프로젝트는 확인 전까지 측정만 수행 |

## 2. 가장 먼저 판단할 것: 수동 조이스틱과 자동 입력의 양립성

자동 블록 시스템 전체의 성립 여부가 이 한 항목에 달려 있으므로, 영상 인식보다 먼저 검증합니다.

- 확인된 사실: 루팅 없이 다른 앱에 터치를 넣는 공개 경로는 사실상 `AccessibilityService.dispatchGesture()`뿐입니다.
- 공식 문서(AccessibilityService#dispatchGesture) 원문: *"Dispatch a gesture to the touch screen. Any gestures currently in progress, whether from the user, this service, or another service, will be cancelled."*
  따라서 **조이스틱을 누른 채 블록 탭을 주입하면 이동이 끊길 가능성이 높다고 추정**합니다. 다만 최근 Android의 다중 입력 장치 처리 변경, 삼성 구현 차이가 있을 수 있어 **추정만으로 결론 내리지 않고** 측정합니다.
- 측정 ④ `TouchProbeActivity` (앱 화면): 왼쪽 손가락을 계속 움직이는 동안 오른쪽에 자동 탭 12회를 주입하고, 조이스틱 포인터가 `ACTION_CANCEL`을 받는지, MOVE 이벤트가 끊기는지, 주입 탭이 도착하는지 기록합니다.
  - CANCELLED ≥ 1회 → 이 방식으로는 "수동 이동 + 자동 블록" **불성립**으로 판단합니다.
  - 유효 시행 5회 이상 모두 SURVIVED → 앱 화면 기준 통과. 게임은 자체 입력 처리를 하므로 ⑤로 다시 확인합니다.
- 측정 ⑤ `InGameTapTest` (게임 화면): 앱은 게임 내부를 볼 수 없으므로 "이동이 끊겼는가"는 사용자가 관찰합니다(다른 기기로 화면 촬영 권장).

④/⑤가 실패할 경우의 대안(모두 **미검증**, 보안 우회 아님):
1. 외부 물리 터치 장치(정전식 오토클리커)를 휴대폰이 신호로 구동 — 실제 손가락과 같은 독립 터치라 다중 터치가 자연스럽지만, 장치 지연은 미확인.
2. 블루투스 HID 게임패드 — 게임이 컨트롤러를 지원할 때만 의미 있음(미확인).
3. 진동/소리로 블록 타이밍만 알려 주고 사람이 누름 — 사람 반응시간이 추가되어 블록 타이밍에는 너무 느릴 가능성이 큼(추정).

## 3. 측정 항목별: 실측 가능 vs 추정만 가능

| 항목 | 앱이 실측하는 것 | 추정/외부 검증이 필요한 것 |
|---|---|---|
| ① 캡처 FPS | 수신 프레임 수, `Image.timestamp` 간격(생산자 시계끼리만 비교), 앱 도착 간격, 소비자 백로그, 초당 FPS | 게임 화면에서 "누락"은 화면이 매 프레임 바뀔 때만 해석 가능. 정확한 고유/중복/누락은 ② 패턴(화면 카운터)에서만 실측 |
| ② 캡처 지연 | 같은 시계(`System.nanoTime`, CLOCK_MONOTONIC)의 Choreographer 시각과 앱 수신 시각의 차; 표시 프레임 대비 몇 리프레시 늦게 들어왔는지(정수, 실측) | 실제 발광 시각은 모름 → "예상 표시시각 기준"은 **추정(±1 리프레시)**. 종단간은 외부 240fps 이상 촬영(ACK 사각형) |
| `Image.timestamp` 사용 | 시계가 같은지 먼저 판정(도착-타임스탬프가 0~150ms 범위·안정적일 때만) | 판정 실패 시 해당 값은 보고하지 않음. 서로 다른 시계를 직접 빼지 않음 |
| ③ 처리시간 | 버퍼 접근 / 전처리 / ROI / 움직임 분석 / 분석 합계 / 콜백 전체, 평균·중앙·p95·p99·최대, 1초 단위 추이 | 설치 직후 ART JIT 상태에 따른 차이 → 워밍업 제외, 반복 측정, 필요 시 `cmd package compile` 후 비교 |
| ④ 모션 감지 | 이벤트 시각, 검출기 확정 지연, 중복 병합 수, 전체화면 모션 억제 프레임 수; 합성 장면에서는 **정답 시작 대비 검출 지연·페이크 반응률** | 실제 게임의 공격 시작 시점은 증거 이미지(이벤트 전후 32프레임)에서 사람이 라벨 → 지연/오탐률. 미검출(재현율)은 외부 영상 필요 |
| ⑤ 입력 충돌 | `ACTION_CANCEL` 수신, MOVE 간격, 주입 탭 도착·지연, deviceId | 게임 화면에서의 결과는 사용자 관찰 |
| 부하/발열 | 앱 자체 CPU 시간(코어 환산), 열 상태, 열 헤드룸, 배터리 온도, (읽을 수 있으면) CPU 주파수 | 시스템 전체 CPU·SoC 온도는 불가 |
| 측정 앱이 게임에 주는 영향 | — | A/B 비교: 앱 없이 / 캡처만 / 캡처+분석 상태에서 게임 FPS를 PC adb 또는 게임 내 표시로 비교 |

## 4. 지연 예산 (블록 판단까지)

```
공격 시작(화면 표시)
  → [A] 표시 → 캡처 수신          ② (추정, 외부 촬영으로 검증)
  → [B] 프레임 분석                ③ (실측)
  → [C] 검출 확정 대기              확정 프레임 수 × 캡처 간격 (④ 합성 시험에서 실측)
  → [D] 블록 시점 예측/대기          미구현 (기술별 블록 가능 구간 데이터 필요)
  → [E] 터치 주입 → 게임 수신        ④의 dispatch→수신 (앱 화면 기준 실측)
  → [F] 게임 입력 처리 + 서버 판정    측정 불가(게임 내부). 핑 20~60ms는 [F]의 일부일 수 있으나 판정 방식 미확인
```

- [C]는 구조적으로 피할 수 없습니다. 캡처가 60FPS라면 확정 2프레임만으로 약 16.7ms, 120FPS라면 약 8.3ms가 추가됩니다.
- 50ms 이내 감지가 되더라도 [D]~[F]와 기술별 블록 가능 구간을 모르면 블록 성공을 보장하지 않습니다.

## 5. 캐릭터별 블록 각도 정보의 영향 (사용자 제공 정보)

- 대부분: 정면 180°, 일부 수비 캐릭터: 정면+측면, 르브론: 360°.
- 의미: 자동 블록은 "상대가 공격을 시작했다"만으로는 부족하고, **그 순간 상대가 내 수비수의 블록 범위 안에 있는지**가 필요합니다. 범위 밖에서 누르면 헛블록(또는 불리한 상태)이 됩니다.
- 필요한 추가 인식: (1) 내 수비수의 화면 위치, (2) 내 수비수가 **바라보는 방향**, (3) 상대 위치. 차분 기반 모션 감지는 (3)의 대략적 위치만 줍니다. (2)는 학습 없는 방법으로 어렵고, 사전학습 자세(pose) 모델 등이 필요할 수 있습니다(미확인).
- 기울어진 카메라 시점에서는 화면상의 각도와 코트상의 각도가 다르므로 보정이 필요합니다.
- 구현 상태: `core/BlockGeometry.kt`에 블록 범위 판정(180° / 측면 포함 270° 가정 / 360°)과 테스트만 있습니다. 측면 포함 캐릭터의 실제 각도는 미확인이라 270°는 자리표시값입니다. 르브론(360°)은 방향 인식 없이도 범위 판정이 가능하므로, **초기 검증 대상 캐릭터로 가장 유리**합니다.

## 6. 하지 않는 것

- 루팅, 보안 우회, 게임 변조, 메모리 읽기, 화면 보안 플래그 우회.
- 대량 학습 데이터 수집. (증거 이미지 라벨링은 소량·선택 사항)
- 서버 인프라. 모든 처리는 기기 내부.
