# DunkBlock Benchmark — 설치 및 측정 절차

이 문서의 순서대로 측정하면, 각 항목이 "실측/추정/불가" 중 무엇인지 구분된 결과 파일이 나옵니다.

## 0. 설치

1. GitHub → Actions → **DunkBlock Benchmark APK** → 최신 성공 실행 → Artifacts의 `DunkBlockBench-apk`(zip) 다운로드.
2. 압축을 풀면 `DunkBlockBench-<커밋>.apk`, `tools/analyze.py`, `docs/`가 있습니다.
3. 휴대폰으로 APK를 옮겨 설치(출처를 알 수 없는 앱 설치 허용 필요).
   - CI가 실행마다 새 디버그 키로 서명하므로, **업데이트 설치가 거부되면 기존 앱을 삭제 후 설치**하세요.
   - 이 APK는 release(디버그 불가) 빌드입니다. 디버그 빌드는 ART 최적화가 줄어 처리시간이 부풀려지므로 측정에 쓰지 않습니다.
4. 첫 실행 시 알림 권한 허용(측정 중 '중지' 버튼이 알림에 있음).
5. ④·⑤ 시험에는 접근성 서비스가 필요합니다. 사이드로드 앱은 Android 13+에서 바로 켜지지 않을 수 있습니다:
   - 설정 → 애플리케이션 → DunkBlock Bench → 우측 상단 ⋮ → **제한된 설정 허용**
   - 설정 → 접근성 → 설치된 앱 → **DunkBlock 입력 충돌 시험** 켜기
   - 이 서비스는 화면 내용을 읽지 않고, 시험 중에만 탭을 보냅니다. 시험 후 끄는 것을 권장합니다.
6. 디스플레이: 설정 → 디스플레이 → 화면 움직임 부드럽게 → **적응형**(120Hz). 표준(60Hz)이면 모든 결과가 60Hz 기준이 됩니다.

### (선택) 측정 정확도 향상
- 설치 직후에는 앱 코드가 JIT 상태라 처리시간이 크게 나올 수 있습니다. 앱이 처음 5초를 자동 제외하지만, PC가 있다면
  `adb shell cmd package compile -m speed -f dev.dunkblock.bench` 후 측정하고 결과에 그 사실을 적으세요.
- 결과 파일 위치: `내장저장소/Download/DunkBlock/<세션>/` (내 파일 앱으로 열람). 원본은 `Android/data/dev.dunkblock.bench/files/sessions/` (`adb pull`).

## 1. 권장 측정 순서

자동 블록 성립 여부를 가장 먼저 가르는 항목부터 진행합니다.

### 1단계 — Phase 0 기록
앱 첫 화면의 "Phase 0 · 기기 확인" 내용을 캡처해 둡니다(Android 버전, 지원 Hz, 열 상태, OpenCV 상태).

### 2단계 — ④ 조이스틱 + 자동 탭 충돌 (앱 화면)
1. "④ 수동 조이스틱 + 자동 탭 충돌 시험" 실행.
2. 왼쪽 영역에 손가락을 대고 **떼지 말고 작은 원을 계속** 그립니다. 1.5초 뒤 자동 탭 12회(10/50/100ms 번갈아)가 시작됩니다.
3. 결과: `touch_probe_summary.txt`, `touch_probe.csv`, `touch_events.csv`.
   - `CANCELLED`가 1회라도 있으면: 현재 방식(dispatchGesture)으로는 수동 이동 + 자동 블록 **불성립**.
   - `LIFTED`, `NO_MOVES`는 판정 불가 시행입니다(손가락을 뗐거나 움직이지 않음). 유효 시행 5회 이상이 될 때까지 반복하세요.
4. 3회 반복 권장(기기 재부팅 후 1회 포함).

### 3단계 — ② 지연·FPS 패턴 시험
"② 지연·FPS 패턴 시험(30초)" → 캡처 동의 화면에서 **전체 화면**을 선택(앱 1개만 공유를 고르면 패턴 화면만 찍히고 회전 시 크기가 바뀔 수 있음).
화면 상단의 흑백 블록 줄(프레임 카운터)과 가운데 흑/백 전환 상자가 나타나고 30초 후 자동 종료됩니다.

권장 조합(각 3회):

| 캡처 배율 | 분석 백엔드 | 목적 |
|---|---|---|
| 1.0 | 캡처만 | 캡처 자체의 최대 FPS·지연 |
| 0.5 | 캡처만 | 해상도가 캡처 FPS·지연에 주는 영향 |
| 0.25 | 캡처만 | 〃 |
| 0.5 | Kotlin | 분석 부하가 캡처에 주는 영향 |
| 0.5 | OpenCV | 〃 |
| 0.5 | 둘 다 | 같은 프레임에서 두 백엔드 처리시간 비교 |

읽는 법(`summary.txt`):
- "패턴 카운터 기반 정확 계수": 화면에 표시된 프레임 중 몇 %가 앱에 도착했는지(**실측**). 50% 근처면 120Hz 화면을 60FPS로 캡처하는 것입니다.
- "표시(예상 프레젠테이션) → 앱 수신 지연": **추정값**(표시 시각이 Choreographer 예상값). 음수가 많으면 예상 표시 시각이 실제보다 늦게 잡힌 것이므로 "vsync 시작 → 수신(상한)"을 함께 보세요.
- "색상 전환 후 새 색이 보이기까지 지난 표시 리프레시 수": 시계 가정 없이 프레임 번호끼리 비교한 값(**실측**).
- "타임베이스 점검": `PLAUSIBLY_SAME_CLOCK`일 때만 `Image.timestamp` 기반 버퍼 나이를 보고합니다.

#### (선택) 외부 고속 촬영으로 종단 간 지연 검증
앱이 알 수 없는 실제 발광 시각을 확인하는 유일한 방법입니다.
1. 설정에서 "카메라 검증용 ACK 사각형"을 켭니다.
2. 다른 휴대폰의 슬로모션(240fps 이상, 가능하면 960fps)으로 S24 Ultra 화면을 촬영하며 ② 시험을 실행합니다.
3. 영상에서 가운데 상자 색이 바뀐 프레임과, 왼쪽 아래 초록 ACK 사각형이 바뀐 프레임 사이의 프레임 수 N을 셉니다.
4. N ÷ 촬영 fps = (발광 → 캡처 감지 → ACK 그리기 → ACK 발광) 시간. 여기서 ACK 표시 지연(대략 1~2 리프레시)을 빼면 캡처 지연의 상한/범위가 됩니다. 240fps 촬영의 분해능은 약 4.2ms입니다.

### 4단계 — ③ 합성 모션 검출 시험
"③ 합성 모션 검출 시험": 코트색 배경에서 블록이 대기하다가 **점프(공격)** 또는 **페이크(짧게 떴다 취소)** 를 무작위로 24회 합니다.
각 시행의 실제 시작 프레임과 그 예상 표시시각이 정답으로 저장됩니다(`truth.csv`).

- 확정 프레임 수 1/2/3 각각 2회 실행 권장.
- 읽는 법: "실제 시작(예상 표시시각) → 검출 확정"이 **화면 변화부터 판단 가능 시점까지의 지연**입니다(합성 장면 한정).
  "페이크 중 이벤트 발생"은 페이크에 반응한 비율로, 지금의 학습 없는 검출기가 페이크를 거르지 못하면 높게 나옵니다(예상).

### 5단계 — ① 실제 게임 세션
1. 설정: 캡처 배율 0.5, 분석 폭 192, Kotlin, 확정 2, HUD 제외 켬, 증거 이미지 켬.
2. "① 게임 캡처 세션 시작" → **전체 화면** 공유 선택 → 게임으로 전환 → 연습/AI 대전에서 수비 위주로 5~10분 → 알림의 '중지'.
3. 같은 조건으로 Wi-Fi / 모바일 데이터 각각 2회. (핑은 캡처·분석 지연과 별개의 지표입니다. 비교는 게임 쪽 영향을 보기 위함)
4. 결과 확인:
   - "검은 화면 프레임 비율"이 높으면 게임이 캡처를 막는 것(FLAG_SECURE)일 수 있습니다. 이 경우 영상 방식 자체가 불가능하며 우회하지 않습니다.
   - `evidence/event_XXXX.png`: 각 이벤트 전 16프레임 + 후 16프레임, 타일마다 이벤트 시작 대비 ms가 적혀 있습니다(빨간 테두리 = 시작/확정 프레임).
5. 게임 FPS 영향(A/B): 같은 장면을 (a) 앱 없이 (b) 캡처만 (c) 캡처+분석으로 플레이하며 게임 FPS를 비교합니다.
   앱은 다른 앱의 FPS를 읽을 수 없으므로, PC가 있으면 `adb shell dumpsys SurfaceFlinger --list`로 게임 레이어 이름을 찾고
   `adb shell dumpsys SurfaceFlinger --latency "<레이어 이름>"`로 프레임 시각을 받습니다(루팅 불필요).

### 6단계 — ⑤ 인게임 자동 탭 시험 (관찰)
1. 게임의 블록 버튼 위치(가로 화면 기준 %)를 입력. 기본값 X 88%, Y 70%는 **추정 위치**이므로 실제 화면에 맞게 수정하세요.
2. "⑤ 인게임 자동 탭 시작" → 대기 시간 안에 게임으로 전환 → 이동 조이스틱을 계속 누른 채 이동.
3. 자동 탭 순간 캐릭터 이동이 끊기는지 관찰(다른 기기로 촬영 권장). 앱은 탭 전송/완료/취소만 기록합니다(`ingame_tap.csv`).
4. 연습 모드에서만 하세요. 대전 모드에서의 자동 입력은 운영정책 위반 소지가 있습니다(미확인).

## 2. 분석 스크립트

PC(파이썬 3.8+, 추가 패키지 불필요):

```
python3 tools/analyze.py Download/DunkBlock/20261110_120000_latency Download/DunkBlock/20261110_121000_motion
python3 tools/analyze.py <게임세션폴더> --labels labels.csv
```

- 세션이 여러 개면 마지막에 비교표를 출력합니다.
- 앱의 `summary.txt`와 독립적으로 원시 CSV에서 다시 계산하므로, 두 값이 다르면 버그 신호입니다.

### 실제 게임 이벤트 라벨링 (선택, 소량)
`evidence/event_0003.png`를 열어 실제 공격이 시작된 타일을 찾고, 그 타일의 ms 값을 적습니다.

```
event_id,label,start_offset_ms
3,DUNK,-58.3
4,NONE,
7,FAKE,-20.1
```

- `NONE` = 막을 필요가 없는 오탐, `FAKE` = 페이크에 반응.
- 실제 시작 → 검출 확정 지연 = (확정 시각 − 검출 시작 시각) − start_offset_ms 로 계산됩니다.
- 분해능은 캡처 프레임 간격(60FPS면 약 16.7ms)입니다.
- 미검출 공격은 이벤트가 없어 라벨할 수 없으므로, 재현율은 별도 영상으로 세야 합니다.

## 3. 결과 해석 기준 (Phase 5 판단용, 임시)

| 결과 | 판단 |
|---|---|
| ④ 또는 ⑤에서 조이스틱 취소/끊김 확인 | AccessibilityService 방식의 "수동 이동 + 자동 블록" 불성립. FEASIBILITY.md 2절의 대안 검토 |
| 게임 세션 검은 화면 | 영상 인식 방식 불가(우회하지 않음) |
| ② 캡처 비율 ≈ 50% (60FPS) | 확정 2프레임만으로 약 17ms 추가. 확정 1프레임은 오탐 증가와 교환 |
| ③ 분석 p95 ≤ 10ms 이고 ② + ③ + 확정 대기 ≤ 50ms | 영상 경로의 속도는 일단 충분. 다음 병목은 공격 종류/페이크 구분과 블록 범위(각도) 판정 |
| ③ 합성 페이크 반응률 높음 | 학습 없는 차분 검출만으로는 페이크 구분 불가 → 경량 모델/자세 추정 도입 검토 |
| 발열로 후반부 FPS·처리시간 악화 | 분석 해상도/주기 낮추기, 백엔드 변경 후 재측정 |
