# 1차 실기기 측정 결과 (2026-11-10)

- 기기: Samsung SM-S928N (Galaxy S24 Ultra, e3q), Android 17 / API 37, 보안패치 2026-10-05
- 표시: 1440x3120 @ 120Hz (지원 모드 120/80/60/48/30/24/10Hz × 3개 해상도)
- 빌드: DunkBlockBench (설정: 캡처 배율 0.5, 분석 폭 192, Kotlin 백엔드, 확정 2프레임)
- 원자료: 전송용 묶음 `DunkBlock_send_20261110_122521.zip` (요약·CSV, 증거 이미지 12장)
- 시작 시 열 상태 2(보통), 열 헤드룸 약 0.85, 배터리 약 40°C. 폰이 식은 상태가 아니었음.

## ④ 수동 조이스틱 + 자동 탭: **실패 (24/24 취소)**

| 항목 | 값 |
|---|---|
| 시행 | 2회 × 12 = 24, 전부 CANCELLED (탭 10/50/100ms 무관) |
| 이벤트 순서 | 실제 손가락(device 6) `ACTION_CANCEL` → 0.3~0.4ms 뒤 주입 탭(device −1) `ACTION_DOWN` |
| 취소 후 | 손가락을 다시 누르기 전까지 실제 손가락 MOVE 0건 |
| 주입 탭 도착 | dispatch → 수신 중앙값 약 5.5ms, 최대 12ms |

결론: `dispatchGesture`로 블록만 주입하면, 화면을 누르고 있는 이동 손가락이 매번 끊긴다. 공식 문서 문구와 일치한다. 다음 시험(⑥)에서는 손가락이 다른 창(접근성 오버레이)에 있어도 끊기는지, 그리고 앱이 조이스틱까지 대신 주입하는 방식이 되는지를 확인한다.

두 번의 추정값이 정확히 1리프레시(약 8.3ms) 차이가 난다. Choreographer의 "예상" 표시시각이 실제 파이프라인 깊이와 회차마다 다르게 맞물리는 것으로 보인다(추정). 따라서 캡처 지연은 "표시와 거의 동시, ±1프레임"까지만 말할 수 있고, 정확한 값은 외부 고속 촬영이 필요하다.

## ③ 합성 모션 검출: **속도는 충분, 민감도 부족**

- 점프 16회 중 9회 검출(56%). 검출 시 실제 시작 → 확정 약 52ms(onset 약 44ms).
- 페이크 8회 중 반응 0회. 단, 페이크를 구분한 것이 아니라 작은 움직임을 못 본 것이다(놓친 점프와 같은 원인).
- 원인: 분석 해상도(가로 192px, 가로 화면에서 192x88)에서 작은 물체의 셀 에너지가 임계(0.06)를 겨우 넘음(정점 0.064). 처리 시간 여유가 커서 해상도를 2~3배 올려도 예산 안이다(추정, 재측정 필요).

## ① 공식경기 1판

- 게임 화면 캡처 가능: 검은 화면 0.4% (FLAG_SECURE 차단 없음).
- 경기 중 캡처 약 120 FPS. 전체 평균 101.7은 로비·로딩(45~60 FPS) 포함.
- 움직임 이벤트 65건/6분 40초, 최장 25초 연속. 3:3 화면 전체 움직임 감지는 공격 인식으로 의미 없음(예상대로).
- 발열: 열 상태 2 → 막판 3(심각), 배터리 39.8 → 42.8°C, 헤드룸 1.085(>1, 스로틀링 예상 구간). 막판 FPS 115 → 102 하락의 원인(결과 화면 vs 발열)은 이 데이터로 구분 불가.
- 이번 묶음의 증거 이미지는 로비 장면뿐이라 경기 중 화면은 미확인.

## 판단

1. 화면 캡처와 분석 속도는 블록 판단의 병목이 아니다.
2. 병목은 입력이다. 접근성 제스처로는 이동 손가락이 끊긴다. 이것이 풀리지 않으면 인식 개선은 의미가 없다.
3. 인식은 해상도·대상(내 선수 주변 + 공) 재설계가 필요하고, 경기 중 스크린샷이 있어야 설계할 수 있다.
