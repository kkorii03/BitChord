VERDICT: ISSUES 7
- HIGH `app/src/main/java/com/music/bitchord/playback/NextTrackPreparation.kt:224` — the 20s deadline is only checked before a step, so `prepareNext`/`awaitHqHead` can run past it into the next track's playback, violating the "finish by end−20s" requirement and leaving no deadline reason. Fix: run the bundle/SYNC step under `withTimeoutOrNull(remaining)` and set `deadlineHit` on timeout.
- MEDIUM `NextTrackPreparation.kt:258` — when AI is enabled, `awaitAiGate` runs before `prepareNext`, delaying the free measurement until 30s and pushing MIX/HQ past the deadline, so mix can be lost on short tracks. Fix: run the free measurement/timing first and gate only the paid `placeWithAi`/`verifySong`/refine calls.
- MEDIUM `NextTrackPreparation.kt:636` — the HQ prefetch is launched in the HQ step and runs concurrently with the SYNC measurement/AI/refine, breaking "one step at a time" and competing with current playback. Fix: serialize or await/cancel the prefetch before starting SYNC.
- MEDIUM `app/src/main/java/com/music/bitchord/playback/smart/LyricsTiming.kt:1647` — `prepareNext` searches only with `query.title to query.artist`, dropping the `artistKnown`/`searchedAs`/`alternatives` names used by the existing path, so covers that do not name the original artist can measure against the wrong recording or fail. Fix: pass/reuse the same candidate-name list as `LyricsController`.
- MEDIUM `LyricsTiming.kt:1643` — the new next-track measurement for a video enters `awaitVideoOpening`'s 250ms `delay` poll loop (up to 30s) for a track that is not playing, violating the no-polling battery rule. Fix: wait on an event/deferred cache-ready signal instead of polling.
- MEDIUM `NextTrackPreparation.kt:421` — `remainingMs` falls back to the next song's `durationMillis()` when the player duration is unknown, so the deadline is computed from the wrong track. Fix: use the current media item's duration or treat unknown as unlimited.
- LOW `NextTrackPreparation.kt:377` — `SyncFacts` does not capture `syncedLyrics`/`recordTimed`/`timedToVideo`, and `fileTimed` is false for video files, so logs can report `no-answer` or `ai-ahead-off` instead of the real skip cause. Fix: derive the reason from the actual gate that prevented the SYNC step.
