(Opus 검토 결과 수정 지시 — 이 브랜치의 '다운로드 곡 굳음 해결'(DownloadHealth, HqLibraryUpgrade 확장)은 방향은 맞지만 아래 결함 8개가 독립 검토자에게 지적됐고 Opus 가 중요도를 확인했다. 다시 만들지 말고 8개를 모두 고친다. 특히 1·3번은 사용자가 가장 짜증낸 '피아노 커버로 굳음'과 '무한 재다운로드'로 직결된다.)
- HIGH `app/src/main/java/com/music/bitchord/download/DownloadHealth.kt:78` — `currentTier` comes from the badge, which is only "FLAC" for every FLAC file, so a hi-res verified file is judged below its own stored `hqTier` and re-downloaded after every replacement; the same bug is at `HqLibraryUpgrade.kt:209/565`. Fix: prefer `meta.hqTier` (or persist depth/rate in the badge) when deriving the current tier.
- HIGH `app/src/main/java/com/music/bitchord/download/HqLibraryUpgrade.kt:257-278` — the fallback force-replaces with an unverified YouTube copy based only on the requested rung, even though the actual rendition can be lower (e.g. 320 AAC → 160 Opus) and no original/sound check ran. Fix: require a verified better pair for manual upgrades, and for repairs verify the served tier is at least the current tier or keep the old file.
- HIGH `app/src/main/java/com/music/bitchord/playback/smart/HqAudioVerify.kt:289-291` — a cached pair acceptance is returned without decoding the file, and `DownloadHealthPolicy.kt:81-84` then skips duration and arrangement checks, so an existing wrong recording whose source pair was once accepted is never condemned. Fix: distinguish cached from fresh acceptance, or run duration/arrangement checks for every file regardless of the cached verdict.
- MEDIUM `app/src/main/java/com/music/bitchord/playback/PlaybackService.kt:9341-9348` — it restreams whenever the verdict is wrong and `localUri` exists, ignoring `DownloadHealthPolicy`'s REDOWNLOAD action, so an offline condemned file is swapped to a network stream and playback stops. Fix: restream only when `outcome.action == STREAM` (online); offline keep the local file or notify the user.
- MEDIUM `app/src/main/java/com/music/bitchord/download/HqLibraryUpgrade.kt:210-221` — `bestEntryFor` is chosen before `wrongSource` is computed and never filters `meta.hqSourceConfigId`, so a repair can re-enqueue the very source that supplied the wrong recording. Fix: compute `wrongSource` first and exclude it inside `bestEntryFor`.
- MEDIUM `app/src/main/java/com/music/bitchord/download/HqLibraryUpgrade.kt:550-558` — `buildPlan` collapses to one best entry before the arrangement filter, so a higher-tier piano cover hides a legitimate lower-tier verified entry and the whole song is dropped. Fix: filter arrangements before `minWith`, or remove the pre-collapse and let `HqLibraryPolicy` group.
- MEDIUM `app/src/main/java/com/music/bitchord/download/DownloadHealth.kt:145` — marking by id without checking the inspected URI is still current means a repair committing during the multi-second verification can mark the new correct file as wrong. Fix: apply the flag only when the current `metadata.uri` still equals the inspected URI, atomically with the record update.
- MEDIUM `app/src/main/java/com/music/bitchord/download/Downloads.kt:1122` — source names are persisted only from the `hq` path, so `SourceStream.trackTitle/trackArtist` from ordinary source downloads are dropped and `DownloadHealth` cannot run the arrangement check on them. Fix: carry the source names through `Route`/`Prepared`/`remember` for every source download.
