작업: 고음질 검사(HqAudioVerify) 후보 다운로드가 HTTP 429 로 연속 실패 — 원인 확정 후 수정. 기준 task/integrate(04bd4a11: abort 수정·취소 수정·재생 중 429 수정 포함).

실제 폰 로그(vc73, 10-26 21시, 곡을 75~90초 간격으로 재생):
21:13:56.094 hq-verify: Golden Monochrome Lossless Provider match=100% offset=0 -> accepted reference=wav candidate=file bytes=19471800
21:13:56.095 hq-tier: Golden Normal 160kbps or below -> Lossless 16-bit 44.1/48kHz from Monochrome Lossless Provider
21:15:00.500 decode: hq-verify failed at=download HTTP 429      (Houdini, 다음 곡)
21:16:28.313 decode: hq-verify failed at=download HTTP 429      (Murder On The Dancefloor)
21:17:57.726 decode: hq-verify failed at=download HTTP 429      (Espresso)
즉 첫 곡은 통과(19.5MB 받음) → 그 곡을 무손실로 재생하는 동안 이후 모든 검사 다운로드가 429.

조사(확정/가설 구분, 파일:줄):
1. 검사 다운로드가 HqVerifyPolicy.bytesToFetch 로 약 19MB(92초 무손실)를 받는다. 같은 서버가 지금 재생 중인 곡 전체도 보내고 있다. 서버가 동시 연결 수나 짧은 시간 전송량으로 막는 것인지 코드·응답 헤더(Retry-After 등)로 확인할 수 있는 만큼 확인. 429 응답의 헤더를 로그에 남기도록(한 줄, URL·키 제외).
2. 429 를 받으면 검사는 'unmeasured' 로 끝나고 언제 다시 시도하는지(같은 재생 중? 다음 재생?) 확인.

수정(확정되는 범위에서, 작고 안전하게):
A. 검사 다운로드 429 → HqRetryPolicy(이미 있는 Retry-After 해석) 로 기다린 뒤 같은 곡 재생 중 1회 재시도(최대 대기 60초, 곡이 바뀌면 취소). 무한 재시도·주기 타이머 금지.
B. 재생 중인 곡과 같은 호스트로 검사 다운로드를 동시에 열지 않기: 현재 곡의 HQ 스트림이 버퍼를 다 채웠거나(ExoPlayer 로딩 완료 이벤트) 곡이 바뀐 뒤에 시작 — 이벤트 기반으로만. 구현이 크면 A 만 하고 B 는 설계 메모로.
C. 비교 구간은 바꾸지 말 것(COMPARE_SECONDS·정렬 수학 변경 금지).
재현 테스트: 429+Retry-After → 대기 후 재시도 1회, 곡 바뀜 → 취소, 두 번째 429 → unmeasured(거절 저장 안 함). 순수 함수 + 기존 HqAudioVerifyCancellationTest 스타일.

절대 금지: featuresOf(...) { !coroutine.isActive } 의 '!' 를 지우지 말 것(abort = 중단해야 하면 true. 이게 반대로 돼서 오늘 품질 업그레이드가 0건이었다).
