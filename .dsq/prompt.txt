== 2차 작업 (현재 브랜치 = 1차 결과) ==
1차 결과를 독립 검토자가 검사한 지적을 전부 고칠 것. 지적이 틀렸다고 판단하면 코드 근거와 함께 요약에 이유를 적고 넘어감.
검토 지적:
VERDICT: ISSUES 6
- **HIGH** `app/src/main/java/com/music/bitchord/playback/smart/HqAudioVerify.kt:546` — `due` is a one-time snapshot, so after one retry gets 429 and `noteRateLimited` sets/extends the host rest, the loop immediately retries the remaining pending songs on that same host, bypassing the rest and causing a 429 burst/battery waste. Fix: re-check `HqHostTracker.restRemainingMs(pending.host)` before each attempt and skip (leave pending) or break for a host that is now resting.
- **MEDIUM** `shared/src/jvmSharedMain/kotlin/com/music/bitchord/data/sources/HqVerifyPolicy.kt:137` — `candidateOrder` calls `isResting` twice per host, and since production `isResting` is clock-based, a rest expiring between the two filters can put an index in neither list, silently dropping that candidate from the race after it was already removed from `running`. Fix: evaluate the predicate once per host into a boolean list and partition indices from that snapshot.
- **MEDIUM** `app/src/main/java/com/music/bitchord/data/sources/addon/AddonClient.kt:368` — the escalated rest returned by `HqHostTracker.noteRateLimited` is discarded and `quietUntilMs` still uses the un-escalated `decision.restMs`, so consecutive 429s do not double this client's own backoff and it hits the same host again at 60s. Fix: use the returned `restMs` (or `HqHostTracker.restRemainingMs(host)`) for `quietUntilMs`.
- **LOW** `app/src/main/java/com/music/bitchord/download/Downloads.kt:1821` — `AutoDownloadDeferred` (thrown at line 1793 when a host is resting after a 429) is not recognized by `rateLimitCode()` and still logs a full stack; manual 429s also log twice (1819 then 2549), so the summary's “429 failures are one line, no stack” claim is not fully backed. Fix: treat `AutoDownloadDeferred` as a deferred/rate-limit case with a single line and avoid re-logging in `friendly()`.
- **LOW** `app/src/main/java/com/music/bitchord/playback/smart/HqAudioVerify.kt:547` — the pending entry is removed before the attempt, so a retry that returns `Abandoned` because the track changed (or fails for a non-429 reason) consumes the one retry without a measurement and is never retried after the rest. Fix: remove the entry only after a definitive attempt, or re-add it when the result is `Abandoned`/non-measurement.
- **LOW** `app/src/main/java/com/music/bitchord/download/Downloads.kt:1807` — `noteSuccess` is called after `work()` even when `transfer` adopted an existing file (`alreadyThere`) without any network request, resetting the host's 429 streak on a non-success. Fix: only note success when bytes were actually fetched, not on an adoption path.
