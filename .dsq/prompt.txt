BitChord 안드로이드 앱(Kotlin, Compose, Media3). 검색은 grep/git grep(rg 없음), 저장소 전체 목록 출력 금지(큰 출력 뒤 멈추지 말고 끝까지). 기준 브랜치 task/fix-1030. 대대적 엄격 검토(사용자: 양보 없는 철저한 검사) — 한 영역을 끝까지 판다.
영역: 무손실 — HqAudioVerify, 재생 중 교체(hq-swap)·다음 곡 무손실 재준비, hq-prefetch·AudioCache 사본 선택, QualityUpgrade·되돌리기·최고 음질 안내·배지, HqLibraryUpgrade(고음질 보관함), 애드온 429. 이전 검토가 남긴 지적(전부 처리):
- MEDIUM — `app/src/main/java/com/music/bitchord/playback/PlaybackService.kt:7476` — `awaitPlayerCondition`'s Boolean result is discarded, so after `UPGRADE_PROVE_MS` expires the code still reads `player.duration` and can call `onProven`, dropping the old loop's timeout-triggered revert. Fix: capture the result and treat `false` as a failed proof (revert) after the pin/URI bail-out.
- MEDIUM — `app/src/main/java/com/music/bitchord/playback/PlaybackService.kt:5756` — The new `StreamChoice` fallback ignores `snapshot.sourceName`, so a snapshot that says "YouTube" but has no `sourceConfigId` can be mapped through a stale substitute choice, unlike `currentIsSubstitute`/`isKnownToBePlayingYouTubesOwn`. Fix: skip the fallback when the snapshot is known to be YouTube (check `sourceName` or reuse the same kind/sourceName logic).
- MEDIUM — `app/src/main/java/com/music/bitchord/playback/PlaybackService.kt:5994` — The pre-adopt abort only calls `releaseStandby()`, leaving the `NerdStats`/`StreamChoice`/`QualityUpgrade` state written at 5952-5957 naming the lossless replacement, so a revert during prepare can leave the direct-YouTube track recorded as lossless with the wrong clock/choice. Fix: call `QualityUpgrade.forgetReverted(mediaId)` and restore/clear the declared format before returning.
- MEDIUM app/src/main/java/com/music/bitchord/download/HqLibraryUpgrade.kt:721 — Forcing `foreground = true` only bypasses the window gate, so `AutomaticRetryPolicy.mayRetry`'s 24h cooldown still makes `prunePlanLocked` delete temporarily parked targets (and `runOne`'s `prunePlan` can then run one early), so the claimed permanent-only pruning is not implemented; the new test uses attempts=0 and misses this. Fix: test permanence directly (`hasCopyAtLeastAsGood` or `attempts >= AutomaticRetryPolicy.MAX_FAILURES`) instead of forcing foreground.
- MEDIUM app/src/main/java/com/music/bitchord/download/Downloads.kt:417 — `publishQueuedIfPending` guards only `_active`, so the following unguarded `DownloadSession.queued` can still run after `onForeground`'s `fail` (or after the service claims the row) and leave the download manager showing Queued/Running with no pending row or service. Fix: perform the pending check and both Queued publishes under the same lock, or have the helper return whether the id is still pending and guard the session update.
- **MEDIUM** `app/src/main/java/com/music/bitchord/playback/smart/HqAudioVerify.kt:518` — `settlesPendingRetry()` treats every `NoReference`/`Unavailable` as definitive, but the live `NoReference` paths are transient (screen-off/head-timeout/decode failure at `:924`, cancellation at `:919`), so the pending 429 retry is consumed without the candidate ever being measured. Fix: carry a reason or attempt count and keep the entry for transient reference/decode/deferral failures, settling only on a second 429 or a real non-measurement.
- **LOW** `app/src/main/java/com/music/bitchord/playback/smart/HqAudioVerify.kt:603` — the loop now removes the entry on the `Outcome.Unavailable` returned by the host-resting deferral at `:357`, so a concurrent same-host download extending the rest between the recheck at `:571` and that check drops the pending retry without any attempt. Fix: return a distinct deferred/Abandoned outcome from the rest check so `settlesPendingRetry` keeps the entry.
