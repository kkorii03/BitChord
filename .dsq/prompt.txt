사용자 로그(어제 13시~오늘 15시, 수백 곡): 'hq-verify: ... -> accepted' 가 0번. 오늘 기준 음원은 WAV 경로로 고쳐졌지만, 이제 후보(고음질) 디코드가 실패한다:
 'W/BitChordAudioDecoder decode: hq-verify failed at=no-first-sample rate=44100 first=false channels=2' (13번) → 'hq-verify: Golden Monochrome Lossless Provider match=0% offset=0 -> rejected' → 'upgrade refused ...: the candidate could not be measured'.
즉 HqAudioVerify.candidateFeatures 가 HQ URL 을 UrlMediaDataSource(MediaDataSource) 로 MediaExtractor 에 넘기면 포맷(44.1kHz 2ch)은 읽지만 샘플을 하나도 못 꺼낸다(네트워크 MediaDataSource 의 getSize/범위 읽기·재열기 문제로 보임).
고칠 것(설계 지정):
 1) 후보는 네트워크에서 직접 디코드하지 말고, 앞부분을 앱 캐시의 임시 파일로 받는다: OkHttp(앱이 HQ 재생에 쓰는 같은 클라이언트·헤더·프록시 규칙) 로 Range 0- 를 요청해 (COMPARE_SECONDS+2)초 분량만큼 받는다. 필요한 바이트 = 스트림 형식의 kbps 가 있으면 kbps*1000/8*(초)*1.2, 없으면 FLAC 기준 최대 40MB 상한. 받는 중 취소 가능.
 2) 그 임시 파일 경로로 MediaExtractor.setDataSource(path) 해서 기존 AudioDecoder 로 디코드(앞부분만 있는 FLAC 은 읽힌다). 끝나면 파일 삭제.
 3) MP4/M4A 처럼 moov 가 뒤에 있어 앞부분만으로 안 열리면 'decode: hq-verify failed at=<단계>' 로그 후 Unavailable(거절 영구 저장 금지).
 4) 실패가 '측정 불가(Unavailable)' 일 때는 HqVerificationStore 에 거절을 저장하지 않는다 — 진짜 불일치(Mismatch)만 저장. 지금 로그의 0% 거절들이 저장소에 쌓였다면, 저장 형식 버전을 올리거나 'match=0 으로 저장된 거절'을 앱 시작 시 한 번 지운다(거절 데이터 정리).
 5) 성공 로그: 'hq-verify: <곡> <소스> match=<n>% offset=<ms> -> accepted|rejected reference=wav candidate=file bytes=<n>'.
 6) 순수 함수(필요 바이트 계산, 거절 저장 여부 판정) jvmTest.
