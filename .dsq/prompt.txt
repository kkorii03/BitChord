BitChord 안드로이드 앱(Kotlin). grep/git grep(rg 없음), 전체 목록 출력 금지. 기준 task/integrate.
버그(폰 로그로 증명): 전에 들은 곡은 AudioCache 에 저음질(opus) 사본이 있어 캐시로 재생 -> 무손실 찾고 HqAudioVerify 통과 -> PlaybackService.kt 약 5778~5792 줄 'upgrade found ... kept for next play; no mid-song swap' -> 다음 재생(보통 40분~2시간 뒤)도 저음질 캐시로 재생돼 영원히 안 바뀜. 손으로 업그레이드하면 swapIn 이 무손실을 캐시에 다 받아('hq-cache: ... fully cached') 그 뒤엔 무손실 캐시가 쓰임.
이전 시도(cloud/fix-hq-cache-replay) 반려 이유: 기억 30분 TTL 이라 실제 사례를 못 고침, 재생 중 실패 시 다른 형식 파일로 같은 바이트 위치에서 이어 읽어 디코딩 깨짐. AudioCache 의 open/read 경로는 이번에 바꾸지 말 것.
설계(Opus 결정): 검증 통과 후 'kept for next play' 하는 그 자리에서, 검증된 무손실 스트림을 백그라운드로 끝까지 캐시에 받아 둔다(손 업그레이드가 쓰는 것과 같은 캐시 키/rendition 태그 방식 재사용, 새 키 체계 만들지 말 것). 그러면 다음 재생 때 cacheKeyOf/completeSibling 이 무손실 사본을 고르게 한다.
할 일: ① swapIn/hq-cache 가 무손실을 캐시에 쓰는 방식과, 다음 재생이 그 항목을 고르는 경로(cacheKeyOf, completeSibling 등)를 먼저 읽고 요약에 적기. ② 같은 곡에 저음질 완전 사본과 무손실 완전 사본이 둘 다 있으면 무손실을 고르도록 보장(지금 순서가 그렇지 않으면 그 판단만 작게 수정, 순수 함수로 빼서 테스트). ③ 무손실 사본이 완전히 받아진 뒤에만 저음질 사본 삭제. ④ 백그라운드 받기는 곡당 1회, 동시 1개, 재생 중인 다른 곡 버퍼링 방해 금지, 실패하면 아무것도 안 바뀜(기존 캐시 유지), 429 는 기존 백오프 따름. ⑤ 로그 한 줄씩: 'hq-prefetch: <id> start <형식>' / 'hq-prefetch: <id> done <MB>' / 'hq-prefetch: <id> failed <이유>', 다음 재생 때 무손실 사본을 고르면 기존 'already playing ... from cache' 줄이 찍히는지 확인.
반드시: 곡 재생 중 교체 정책 그대로. 다운로드된 곡·커버 곡·MV 판정 경로 건드리지 말 것. 배터리: 폴링·타이머 금지, 이벤트 기반. 바꾼 함수의 모든 호출부·타입 다시 확인. 기존 코드 의도(주석)를 지우면 요약에 이유.
테스트: ②의 선택 함수 단위 테스트(저음질만 -> 저음질, 둘 다 완전 -> 무손실, 무손실 부분만 -> 저음질). 새 app 테스트 이름을 요약에 적을 것.
제약: .github/, keys, 서명 수정 금지. 10줄 이내 요약: 수정 파일 / 핵심 변경 / 테스트 결과 / 미해결 문제.
